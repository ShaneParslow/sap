### Update Config Skill

Modify Claude Code configuration by updating settings.json files.

#### When Hooks Are Required (Not Memory)

If the user wants something to happen automatically in response to an EVENT, they need a **hook** configured in settings.json. Memory/preferences cannot trigger automated actions.

**These require hooks:**
- "Before compacting, ask me what to preserve" → PreCompact hook
- "After writing files, run prettier" → PostToolUse hook with Write|Edit matcher
- "When I run bash commands, log them" → PreToolUse hook with Bash matcher
- "Always run tests after code changes" → PostToolUse hook

**Hook events:** PreToolUse, PostToolUse, PreCompact, PostCompact, Stop, Notification, SessionStart

#### CRITICAL: Read Before Write

**Always read the existing settings file before making changes.** Merge new settings with existing ones - never replace the entire file.

#### CRITICAL: Use AskUserQuestion for Ambiguity

When the user's request is ambiguous, use AskUserQuestion to clarify:
- Which settings file to modify (user/project/local)
- Whether to add to existing arrays or replace them
- Specific values when multiple options exist

#### Decision: /config command vs Direct Edit

**Suggest the `/config` slash command** for these simple settings:
- `theme`, `editorMode`, `verbose`, `model`
- `language`, `alwaysThinkingEnabled`
- `permissions.defaultMode`

**Edit settings.json directly** for:
- Hooks (PreToolUse, PostToolUse, etc.)
- Complex permission rules (allow/deny arrays)
- Environment variables
- MCP server configuration
- Plugin configuration

#### Workflow

1. **Clarify intent** - Ask if the request is ambiguous
2. **Read existing file** - Use Read tool on the target settings file
3. **Merge carefully** - Preserve existing settings, especially arrays
4. **Edit file** - Use Edit tool (if file doesn't exist, ask user to create it first)
5. **Confirm** - Tell user what was changed

#### Merging Arrays (Important!)

When adding to permission arrays or hook arrays, **merge with existing**, don't replace:

**WRONG** (replaces existing permissions):
```json
{ "permissions": { "allow": ["Bash(npm *)"] } }
```

**RIGHT** (preserves existing + adds new):
```json
{
  "permissions": {
    "allow": [
      "Bash(git *)",      // existing
      "Edit(.claude)",    // existing
      "Bash(npm *)"       // new
    ]
  }
}
```

#### Settings File Locations

Choose the appropriate file based on scope:

| File | Scope | Git | Use For |
|------|-------|-----|---------|
| `~/.claude/settings.json` | Global | N/A | Personal preferences for all projects |
| `.claude/settings.json` | Project | Commit | Team-wide hooks, permissions, plugins |
| `.claude/settings.local.json` | Project | Gitignore | Personal overrides for this project |

Settings load in order: user → project → local (later overrides earlier).

**Permission Rule Syntax:**

- Prefix wildcard: `"Bash(git *)"` - matches `git`, `git status`, `git commit`, etc.

- File paths: `"Edit(src/**)"` - path rules in `permissions` use `Edit(path)` for every file-writing tool (Write, Edit, NotebookEdit) and `Read(path)` for reads. `Write(path)`, `NotebookEdit(path)` and `Glob(path)` rules are not matched by file permission checks. Bare tool names (`"Write"`), deny/ask `Tool(param:value)` rules and hook `if` conditions still use each tool's own name

#### Hooks Configuration

Hooks run commands at specific points in Claude Code's lifecycle.

##### Hook Structure
```json
{
  "hooks": {
    "EVENT_NAME": [
      {
        "matcher": "ToolName|OtherTool",
        "hooks": [
          {
            "type": "command",
            "command": "your-command-here",
            "timeout": 60,
            "statusMessage": "Running..."
          }
        ]
      }
    ]
  }
}
```

##### Hook Events

| Event | Matcher | Purpose |
|-------|---------|---------|
| PermissionRequest | Tool name | Run before permission prompt |
| PreToolUse | Tool name | Run before tool, can block |
| PostToolUse | Tool name | Run after successful tool |
| PostToolUseFailure | Tool name | Run after tool fails |
| Notification | Notification type | Run on notifications |
| Stop | - | Run when Claude stops (including clear, resume, compact) |
| PreCompact | "manual"/"auto" | Before compaction |
| PostCompact | "manual"/"auto" | After compaction (receives summary) |
| UserPromptSubmit | - | When user submits |
| SessionStart | - | When session starts |

**Common tool matchers:** `Bash`, `Write`, `Edit`, `Read`, `Glob`, `Grep`

##### Hook Types

**1. Command Hook** - Runs a shell command:
```json
{ "type": "command", "command": "prettier --write $FILE", "timeout": 30 }
```

**2. Prompt Hook** - Evaluates a condition with LLM:
```json
{ "type": "prompt", "prompt": "Is this safe? $ARGUMENTS" }
```
Only available for tool events: PreToolUse, PostToolUse, PermissionRequest.

**3. Agent Hook** - Runs an agent with tools:
```json
{ "type": "agent", "prompt": "Verify tests pass: $ARGUMENTS" }
```
Only available for tool events: PreToolUse, PostToolUse, PermissionRequest.

##### Hook Input (stdin JSON)
```json
{
  "session_id": "abc123",
  "tool_name": "Write",
  "tool_input": { "file_path": "/path/to/file.txt", "content": "..." },
  "tool_response": { "success": true }  // PostToolUse only
}
```

##### Hook JSON Output

Hooks can return JSON to control behavior:

```json
{
  "systemMessage": "Warning shown to user in UI",
  "continue": false,
  "stopReason": "Message shown when blocking",
  "suppressOutput": false,
  "decision": "block",
  "reason": "Explanation for decision",
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "Context injected back to model"
  }
}
```

**Fields:**
- `systemMessage` - Display a message to the user (all hooks)
- `continue` - Set to `false` to block/stop (default: true)
- `stopReason` - Message shown when `continue` is false
- `suppressOutput` - Hide stdout from transcript (default: false)
- `decision` - "block" for PostToolUse/Stop/UserPromptSubmit hooks (deprecated for PreToolUse, use hookSpecificOutput.permissionDecision instead)
- `reason` - Explanation for decision
- `hookSpecificOutput` - Event-specific output (must include `hookEventName`):
  - `additionalContext` - Text injected into model context
  - `permissionDecision` - "allow", "deny", or "ask" (PreToolUse only)
  - `permissionDecisionReason` - Reason for the permission decision (PreToolUse only)
  - `updatedInput` - Modified tool input (PreToolUse only)

#### Constructing a Hook (with verification)

Given an event, matcher, target file, and desired behavior, follow this flow. Each step catches a different failure class — a hook that silently does nothing is worse than no hook.

1. **Dedup check.** Read the target file. If a hook already exists on the same event+matcher, show the existing command and ask: keep it, replace it, or add alongside.

2. **Construct the command for THIS project — don't assume.** The hook receives JSON on stdin. Build a command that:
   - Extracts any needed payload safely — use `jq -r` into a quoted variable or `{ read -r f; ... "$f"; }`, NOT unquoted `| xargs` (splits on spaces)
   - Invokes the underlying tool the way this project runs it (npx/bunx/yarn/pnpm? Makefile target? globally-installed?)
   - Skips inputs the tool doesn't handle (formatters often have `--ignore-unknown`; if not, guard by extension)
   - Stays RAW for now — no `|| true`, no stderr suppression. You'll wrap it after the pipe-test passes.

3. **Pipe-test the raw command.** Synthesize the stdin payload the hook will receive and pipe it directly:
   - `Pre|PostToolUse` on `Write|Edit`: `echo '{"tool_name":"Edit","tool_input":{"file_path":"<a real file from this repo>"}}' | <cmd>`
   - `Pre|PostToolUse` on `Bash`: `echo '{"tool_name":"Bash","tool_input":{"command":"ls"}}' | <cmd>`
   - `Stop`/`UserPromptSubmit`/`SessionStart`: most commands don't read stdin, so `echo '{}' | <cmd>` suffices

   Check exit code AND side effect (file actually formatted, test actually ran). If it fails you get a real error — fix (wrong package manager? tool not installed? jq path wrong?) and retest. Once it works, wrap with `2>/dev/null || true` (unless the user wants a blocking check).

4. **Write the JSON.** Merge into the target file (schema shape in the "Hook Structure" section above). If this creates `.claude/settings.local.json` for the first time, add it to .gitignore — the Write tool doesn't auto-gitignore it.

5. **Validate syntax + schema in one shot:**

   `jq -e '.hooks.<event>[] | select(.matcher == "<matcher>") | .hooks[] | select(.type == "command") | .command' <target-file>`

   Exit 0 + prints your command = correct. Exit 4 = matcher doesn't match. Exit 5 = malformed JSON or wrong nesting. A broken settings.json silently disables ALL settings from that file — fix any pre-existing malformation too.

6. **Prove the hook fires** — only for `Pre|PostToolUse` on a matcher you can trigger in-turn (`Write|Edit` via Edit, `Bash` via Bash). `Stop`/`UserPromptSubmit`/`SessionStart` fire outside this turn — skip to step 7.

   For a **formatter** on `PostToolUse`/`Write|Edit`: introduce a detectable violation via Edit (two consecutive blank lines, bad indentation, missing semicolon — something this formatter corrects; NOT trailing whitespace, Edit strips that before writing), re-read, confirm the hook **fixed** it. For **anything else**: temporarily prefix the command in settings.json with `echo "$(date) hook fired" >> /tmp/claude-hook-check.txt; `, trigger the matching tool (Edit for `Write|Edit`, a harmless `true` for `Bash`), read the sentinel file.

   **Always clean up** — revert the violation, strip the sentinel prefix — whether the proof passed or failed.

   **If proof fails but pipe-test passed and `jq -e` passed**: the settings watcher isn't watching `.claude/` — it only watches directories that had a settings file when this session started. The hook is written correctly. Tell the user to open `/hooks` once (reloads config) or restart — you can't do this yourself; `/hooks` is a user UI menu and opening it ends this turn.

7. **Handoff.** Tell the user the hook is live (or needs `/hooks`/restart per the watcher caveat). Point them at `/hooks` to review, edit, or disable it later. The UI only shows "Ran N hooks" if a hook errors or is slow — silent success is invisible by design.

#### Troubleshooting Hooks

If a hook isn't running:
1. **Check the settings file** - Read ~/.claude/settings.json or .claude/settings.json
2. **Verify JSON syntax** - Invalid JSON silently fails
3. **Check the matcher** - Does it match the tool name? (e.g., "Bash", "Write", "Edit")
4. **Check hook type** - Is it "command", "prompt", or "agent"?
5. **Test the command** - Run the hook command manually to see if it works
6. **Use --debug** - Run `claude --debug` to see hook execution logs

You can use an enum. Rust's `core` just has no generic `Atomic<T>`, only fixed integer atomics like `AtomicU8`, so you store the enum as a `u8` and convert it back when you load it. The usual way is a `#[repr(u8)]` enum with a conversion function; there are also crates like `atomic_enum` that generate it for you.

Your reasoning about why it's atomic is slightly off, though:

- **Why atomic:** Rust won't let you mutate a plain `static` without `unsafe` (`static mut`). An atomic is the safe way to have a mutable global. A one-byte store is a single instruction on RISC-V, so an interrupt can't land in the middle of it anyway.
- **Why `Relaxed`:** it's fine even with several harts. Every hart that probes gets the same answer and stores the same value, and no other data is published through this variable. The worst case is probing twice. That's what makes `Relaxed` correct, not the absence of threads.

**Your "fuse off" idea** is real, and it already exists in three forms:

- **Kernel "alternatives":** this is almost exactly what you described. Linux writes the instruction variants into the kernel image and, at boot, patches in the right ones for the detected CPU features or known chip bugs. RISC-V Linux uses its `ALTERNATIVE` macros this way for Zbb (bit manipulation), Svpbmt (page memory types) and vendor errata. On x86 the same mechanism lives in `alternative.c`.
- **Static keys / jump labels:** a `nop` at the decision point gets patched into a jump (or back) at runtime. The common path then costs nothing, not even a branch.
- **Function multiversioning:** the compiler clones only the functions that benefit from a feature, and a resolver picks one clone once, at load time. GCC and Clang do this with `target_clones` and ELF `ifunc`; in Rust there's the `multiversion` crate. Your deduplication guess is right: only the functions that differ get duplicated, and everything else is shared.

The catches:
- Do the patching before kernel code is mapped read-only and execute-only.
- After patching, run `fence.i` (the RISC-V instruction that resyncs instruction fetch) on every hart that might have fetched the old code.
- Choose feature sets per function instead of compiling every combination, because the number of combinations grows exponentially.
- It only covers differences at the instruction level. CHERI changes pointer width and the ABI, so it still needs its own build.
- None of this is worth it for the console, where one predictable branch per write costs nothing.

**Device trees**

Yes, Arm uses device trees too, on embedded boards and most SoCs. Arm servers and many Arm laptops use ACPI instead, and RISC-V server platforms are adding ACPI alongside device trees.

x86 uses ACPI tables plus PCI enumeration. Part of what makes x86 messy is that ACPI isn't just data: it includes AML, a bytecode you have to interpret to find some devices and to do power management. The reference interpreter is a large C codebase. A minimal x86 kernel can avoid it by reading only the memory map and the table listing CPUs and interrupt controllers, and finding devices through PCI. A device tree is pure data, with nothing to execute.

**The format** is one big-endian blob:
- **Header:** magic number `0xd00dfeed`, total size, and offsets to the other blocks.
- **Reserved-memory list:** address/size pairs the OS must not use.
- **Structure block:** a stream of tokens that open and close nodes and carry properties.
- **Strings block:** the property names, which properties point into by offset.

A device's `reg` property is a list of address/size pairs. How many 32-bit cells make up each address and size comes from properties on the *parent* node, which is the one non-obvious rule.

**Minimal parser:** about 200–300 lines of `no_std` Rust with no allocation:
1. Check the magic number and bounds-check every offset against the total size.
2. Walk the token stream once, tracking the current path and borrowing names and values straight from the blob.
3. Pull out only what the kernel needs:
   - **Clock rate:** under `/cpus`, which replaces the hard-coded 10 MHz.
   - **RAM ranges:** from `/memory`.
   - **Reserved regions:** OpenSBI reserves its own memory this way.
   - **Hart count.**
   - **Devices found by their `compatible` string:** QEMU's test device (the fix for the exit status), the interrupt controller, and the virtio devices.

The `fdt` crate does exactly this already.

**Complete parser:** what Linux does on top of that:
- Builds an in-memory tree with an index of node cross-references, so lookups aren't linear scans.
- Follows those cross-references for interrupts, clocks, resets and GPIOs.
- Translates addresses through every bus between a device and the CPU.
- Routes interrupts, including PCI's interrupt mapping.
- Skips devices marked disabled.
- Matches drivers against `compatible` lists, most specific first.
- Handles aliases and overlays applied at runtime.

It's large because it serves every driver on every board.

**For sap:** that split maps onto the microkernel design. The kernel needs only the minimal parser, for RAM, reservations, clock rate, hart count, interrupt controller and console. A userspace device manager would do the complete parse and give each driver component capabilities for exactly its device memory and interrupts. Drivers never read firmware tables, and an ACPI port later would just be a second userspace producer, with the AML interpreter kept out of the kernel. seL4 instead turns the device tree into kernel configuration at build time; parsing at run time keeps one kernel binary for many boards.

I filed this as `hw-device-discovery` (proposed) and added minimal device-tree parsing to M2, because Sv39 page tables need the RAM ranges.

Decision for you: write the minimal parser yourself or use the `fdt` crate? It's small and teaches the format, which suits an own-kernel project, and I'd lean toward writing it. The crate is the faster option.

#### Supporting other architectures

**Mostly portable.** Everything above the kernel is architecture-neutral: components, Cap'n Proto interfaces, IPC conventions and the object store, so porting those means changing the compile target. What doesn't port is the kernel's architecture layer: boot entry, trap entry and exit, context switching, page tables, timer, interrupt controller, cross-CPU interrupts, and TLB and cache maintenance. CHERI is the other exception: it only exists on RISC-V and Arm's Morello board, so on x86 it simply isn't there. The design already treats CHERI as optional, so it isn't a blocker.

**x86 is tractable, and the microkernel is why.** Most of x86's mess either stays in a bounded architecture layer or never enters the kernel:
- **Boot:** UEFI or the Limine boot protocol (a ready-made x86 boot loader that hands the kernel a standard set of information) skips the legacy real-mode chain entirely. You start in 64-bit mode with a memory map, the ACPI root pointer and a framebuffer, and Limine can start the other CPUs for you. That makes it about as simple as OpenSBI makes RISC-V.
- **CPU setup:** x86 has more pieces to set up than RISC-V: descriptor tables, the interrupt controllers (local APIC and IOAPIC), and calibrating the CPU clock as a timer. They're well documented and written once. I'd guess the x86 layer ends up two to three times the size of the RISC-V one, but bounded. seL4 runs one design on x86-64, Arm and RISC-V, which shows the kernel interface can be shared.
- **ACPI:** the kernel only needs the static tables: the memory map and the table listing CPUs and interrupt controllers. The AML interpreter, the really messy part, goes in a userspace component, the way Genode does it.
- **Recurring cost:** speculation mitigations on kernel entry. That's the main ongoing performance cost x86 adds for a microkernel.
- **Memory ordering:** x86's memory ordering is stricter than RISC-V's or Arm's. Code that is correct on RISC-V is correct on x86, but not always the other way round, so developing on RISC-V first is the right order.

**Drivers are the real limit on every architecture.** Standard PC hardware is fairly easy: NVMe, SATA, USB host controllers, HD Audio, and the UEFI framebuffer. The hard parts are:
- GPUs (Intel is the most documented)
- Wi-Fi
- laptop power management: suspend and resume, and battery, all done through AML
- the long tail of network and Bluetooth chips

The design's answer is a contained Linux virtual machine that drives that hardware. The hardware is handed to it directly, with the IOMMU restricting which memory those devices can reach, and sap talks to it through typed interfaces. That needs virtualization support in the kernel, which NOVA, Genode and Qubes have done before.

**PCs may be friendlier than Arm.** PC buses are standardized; Arm laptops boot with ACPI and use bespoke chips whose Linux support is itself still arriving. So it doesn't have to wait for Arm adoption. Desktops and virtual machines first, laptops last, because of power management.

**Suggested order:**
1. When paging and context switching land, keep the architecture interface narrow and explicit.
2. Do x86-64 as the second port once IPC works (around M5), so the abstraction gets tested early. Target QEMU's `q35` machine with OVMF (QEMU's UEFI firmware) and Limine.
3. Then real hardware: an Intel-GPU desktop or mini PC with NVMe and wired Ethernet.

Genode/Sculpt and Redox already run on real x86 machines.

I went through your questions against the wiki and against seL4's source (I cloned seL4, Microkit and rust-sel4). The answers are filed as seven new wiki pages; everything is proposed or exploring until you decide. Overall: the tangle mostly comes from three different kinds of capability being treated as one. Network and the store need only four format decisions now. Program loading touches the architecture much less than you feared.

**seL4, closer look** ([kernel-sel4-differences](docs/kernel/kernel-sel4-differences.md))
- **Worse than the wiki said:** a message delivers only **one** real capability, not "a few". The receiver names a single receive slot, and the transfer code stops using it after the first capability. Transfers are also copies, so the sender keeps its own.
- **Device tree is not a problem:** seL4 compiles the device tree into one kernel per platform and passes the blob to the first user program at boot.
- **Desktop fit:** nothing in the kernel is hostile to a desktop. What's missing is mostly userspace work you'd do on any kernel: spawning processes, balancing threads across cores (it pins threads and uses one big kernel lock), and an interactive scheduling policy.
  - The real kernel gaps are power management (suspend, frequency scaling), any virtualization on RISC-V, and CHERI.
  - Its multicore, IOMMU and budget-scheduling (MCS) configurations aren't covered by the proofs.
  - Microkit is static, at most 63 components, so it can't run a desktop.
  - Genode's Sculpt desktop runs on seL4, but only as an experimental image; its main users run their own kernels.
- **Sketch on seL4?** I'd say no.
  - Its limits would push the IPC design toward workarounds you'd later remove.
  - The remaining kernel milestones (paging, user mode, capability tables, IPC) are the well-trodden part, and we're copying seL4's design for them anyway.
  - Instead, read seL4's code at each milestone. The fallback if our kernel stalls is a thin crate exposing sap's kernel interface, implemented over seL4.

**Process capabilities** ([cap-process-authority](docs/capabilities/cap-process-authority.md))
- **One table:** a process has a single kernel capability table. Calls to other processes' objects are built on entries in it. Stored capabilities only become live when you read them through the store.
- **Not capabilities:** interface specs are types, memory regions are mappings or frames, and store data is reached through a capability, not held.
- **How objects arrive:** every object arrives in a message. The bootstrap message comes first, and the process traverses outward from it, including through store refs. So yes, it is what you described.
- **Your kernel-imports idea:** kernel object methods get described in a Cap'n Proto schema, as seL4 does in XML, so a driver can import a register frame and an interrupt handler like any other interface.
  - Ordinary programs never import kernel objects: their address space, memory budget and thread are runtime capabilities handled by the Rust runtime.
  - A program that asks for kernel objects is visibly asking for more authority.

**Send/receive/signal** ([ipc-cap-transfer](docs/ipc/ipc-cap-transfer.md))
- They are the kernel half of IPC: endpoints for synchronous calls (which can carry capabilities and lend the caller's CPU time), notifications as doorbells. The rings are built on them.
- **Gap this exposes:** capabilities can't travel through shared memory. The proposal:
  1. The sender makes one syscall that moves or copies a batch of capabilities into slots the receiver set aside for that connection.
  2. Then it publishes the ring message, which refers to those slots.
  3. Messages without capabilities, the vast majority, still cost no syscall.

**Program loading** ([prog-loading](docs/programs/prog-loading.md))
- **Who loads:** a userspace process manager, as in seL4. I'm proposing the "process factory" becomes its interface rather than a kernel object.
- **Formats:**
  - Native code is static, position-independent ELF.
  - Wasm and Linux binaries are handled by loader components, which matches your "driver per format".
  - The per-architecture part is a small startup convention: entry registers, stack, thread pointer.
- **Flat address space:** no, each process gets its own. A shared one mainly buys pointers that mean the same thing everywhere, and Cap'n Proto's relative offsets already give you that. RISC-V's 39-bit addressing also leaves only 512 GiB for everything.
- **Boot:** the process manager needs the store to find code, but the store is itself a program. A boot image of initial code breaks that loop.

**Is the store purely userspace?** As far as the kernel knows, yes: it uses only ordinary frames, endpoints and notifications. It's special because of where it sits (it holds every stored token, and loading depends on it), not because of kernel support.

**Network RPC and the store across machines** ([ipc-network-rpc](docs/ipc/ipc-network-rpc.md), [store-distribution](docs/store/store-distribution.md))
- **Protocol:** Cap'n Proto RPC between machines identified by public keys, carried by one bridge component, so local programs never contain network code.
- **Is Cap'n Proto RPC good enough?** Yes, with one gap: no implementation does three-party handoff, where the recipient connects to the hosting machine directly instead of through whoever passed the capability on.
  - That matters when your phone grants a website access to data on your home server: without handoff, the site's calls go through the phone.
  - Workaround: pass persistent references (sturdy refs) across machines.
  - OCapN (a spec effort for exactly this network layer) is the model to copy.
- **Where data lives:** values copy freely between your machines. Each mutable ref has one machine that orders its updates. Offline edits merge by rules declared in the schema, never last-writer-wins.
- **Websites:** a gateway hands out scoped, expiring, revocable URLs through the powerbox.
- **Your config elsewhere:** keybinds are values under your root, so a new machine has them after its first sync. Someone else's machine gets a small, expiring read-only grant. Live reload comes from subscribing to the ref.
- **Decide now for the store** (the rest can wait):
  1. Sturdy refs name their host machine's key.
  2. Hashes carry an algorithm tag.
  3. Stored values never contain machine-local identifiers.
  4. Each ref has one authoritative machine.

**Use cases** ([store-use-cases](docs/store/store-use-cases.md)) covers roaming config, a website, the system agent, phone/desktop/server roles, and Linux.
- **System agent:** it works on a branch of refs, and you review a typed diff and accept it with one atomic multi-ref update, so undo is free. That's the store's strongest argument over a file system, and it adds atomic multi-ref updates to the store's requirements.
- **Adoption path, not yet discussed:** the store, bridge and gateway are ordinary programs that could also run on Linux and macOS before sap runs on real hardware.

You mean the whole object graph: transient, persistent and remote objects, with disk and network as backends. **Does the kernel have to get involved in the store?** Partly, and that's where the line falls:
- **What the kernel does:** every reference between processes is a kernel capability (an endpoint, or a channel's frames and notifications). Only the kernel can create or move one, so unforgeability comes from the kernel.
- **What it doesn't see:** the graph. No hashes, values, refs or schemas. Each object has one host process, and that host tracks its objects and what it has handed out, the way seL4 servers do.
- **Revocation works at both levels:** cutting off a client is the kernel deleting its connection capability; revoking one object is the host dropping it.
- **Per-object kernel enforcement is optional:** a host that wants it mints a separately badged endpoint per object, paying a kernel table entry per object from its own memory quota.
- **The alternative** is the kernel owning the graph, as KeyKOS and EROS did. That's the all-or-nothing approach we already rejected.

Your model also simplifies two things:
- **Persisting** something just means handing it to a persistent host. A value's hash doesn't change, so nothing that refers to it breaks.
- **A ref's authoritative machine** is simply the machine its host runs on.

**Network.** Yes, the conclusion is that it pushes facts into schemas, and annotations are the right carrier. I added two next to `$own`/`$borrow`, both enforced by whoever stores or transmits the value, like ownership:
- **`$merge(rule)`:** how concurrent offline updates to a ref combine. Without it, a conflict keeps both versions.
- **`$local`:** marks a field that is meaningful only on one machine.

On the Urbit comparison: it's the same "a key is your address" idea without Urbit's registry or scarcity. Any machine can make a key, and a name containing it can be checked without asking anyone; Tor onion addresses work the same way. 1. Capability fields, the normal way to refer to anything, never contain local ids, because they're converted automatically.
2. `$local` fields get rejected when a value is persisted or sent off the machine.
3. Review and lints catch the rest.

- **CHERI's main speed gain needs a shared space.** Components call each other with no page-table switch and no TLB flush.
- **Paging stays either way.** CHERI systems still use page tables for scattered physical memory, sharing frames, guard pages and devices. A shared space saves the *switching*, not the paging.
- **Without CHERI, a shared space saves nothing,** because each protection domain still needs its own page table.

Also, 512 GiB is only a limit when everything shares one Sv39 space. Sv48 (256 TiB) is in QEMU and newer RISC-V cores.

- Components never assume they own their address space.
- Code is position-independent, and buffer and stack addresses come from the startup record rather than fixed addresses.
- The process manager decides placement: one component per address space on paging-only hardware, many CHERI compartments per address space (up to all of them) on CHERI hardware.

Agreed on both points. The edge cases are real, and deciding all of it either in the process manager or in programs loses something. I think the way out is that "start the server" is really three separate decisions. That's a new page, [prog-composition](docs/programs/prog-composition.md), still exploring.

1. **Which server, decided at launch.** Each declared import is matched to an instance when the consumer is launched. The wiring is automatic and visible, and a missing implementation fails at launch, not on first call. This keeps the benefit you want from declared interfaces.
2. **Shared or private.** One instance for the whole system or user, a fresh one per consumer, or a capability the launcher already holds.
3. **When to start.** Lazy (on first call) by default, eager for things needed immediately, manual otherwise.

Wiring at launch but starting lazily covers your "maybe it isn't actually needed" case: nothing runs until it's called, but nothing is left unresolved either.

**Fine-grained control without leaving the model.** A program that wants to control how its server starts (arguments, how many, when) imports a *factory* for the interface instead of the interface itself. The factory is still a declared import, so the program still states its dependency, but the start decision is the program's. "Let processes handle starting things" becomes one option within the declarative model, not an escape from it.

**The wiring is data.** A "composition" value in the graph lists which components run, how each import is routed, and each one's start policy. The process manager carries it out, and the system agent and the package registry edit it. Fuchsia does almost exactly this: manifests route capabilities between components, which start lazily by default with eager start as an opt-in. It's the closest prior art.

**Edge cases:**
- **Cycles:** lazy start breaks them; eager cycles are rejected when the wiring is resolved.
- **Many callers at once:** they all queue on one endpoint in the kernel, and only one instance starts.
- **Hung server:** this isn't specific to on-demand start, since any server can hang.
  - Calls carry deadlines, so callers don't get stuck.
  - The supervisor gives a new server a deadline to reach its first receive, then kills and restarts it per policy, like Erlang supervisors.
- **Idle stop:** a server stops only while it's waiting to receive. Calls that arrive meanwhile queue in the kernel and trigger the next start, so none are lost.
- **Authority:** a lazily started server's own imports come from the wiring, never from whoever called first, so the first caller can't shape the server's authority.

**Names are done.** Across the wiki, "graph" now means every object, "store" its persistent part, and "home node" a ref's authoritative machine. The glossary notes that "home" has nothing to do with Unix home directories. Lint is clean apart from the two kernel pages flagged by your uncommitted comments.
