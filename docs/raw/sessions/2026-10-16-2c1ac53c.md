#### 1. seL4 concepts, in the order you need them

1. **Capability.** An entry in a table that only the kernel can write: [Cap in kernel/cap.rs](kernel/cap.rs#L22). A program never holds the capability itself, only its **slot number** in the table (a *CPtr*, short for capability pointer). Programs can't make up authority, because the only thing they can name is a slot the kernel already filled.
2. **CNode, CSpace, CPtr.** A **CNode** is an array of 64-byte slots. A thread's **CSpace** (capability space) is the tree of CNodes reachable from its root CNode. The kernel resolves a CPtr by walking that tree, like a page-table walk ([cspace.rs](kernel/cspace.rs)). In `init` the tree is a single level, so a CPtr is simply a slot number. That's why `SlotRef::new(root, i)` uses the depth `WORD` = 64 ([cnode.rs](user/libsap/cnode.rs#L10)).
3. **Untyped memory and retype.** The kernel never allocates memory for itself. At boot it hands the root task capabilities to raw "untyped" memory. Userspace calls `retype` on them to create every object: threads, CNodes, endpoints, page tables, frames.
4. **Derivation tree.** Every copy of a capability is recorded as a child of the capability it came from. `revoke` deletes all descendants. This is why revoking the untyped memory a process was built from destroys the whole process ([process.rs](user/libsap/process.rs)).
5. **Thread (TCB, thread control block).** Holds a CSpace root, an address space (VSpace) root, an IPC buffer and a priority.
6. **Endpoint.** A meeting point for synchronous messages. It has no buffer: a sender waits until a receiver arrives, or the reverse, and then the kernel copies the message directly from one to the other.
7. **Notification.** One word of bits plus a queue of waiting threads. `Signal` ORs bits into the word without blocking; `Wait` blocks until the word is nonzero. It works as a doorbell and carries no data.
8. **Reply object (MCS).** How a `Call` gets answered. More in §5.

##### Badges

Badges aren't kernel-internal; the whole point is that userspace sees them. A badge is a word the kernel stamps on a capability when it is *minted* (`CNODE_MINT`). Once stamped, it can't be changed or forged. Whenever someone uses that capability, the kernel delivers the badge to the other side:
- **Endpoints:** the receiver gets the sender's badge in `a0`. A server gives each client (or each object it serves) a differently badged copy of one endpoint. The badge then tells the server "this is client 7" or "this is open file #3", over a single endpoint. In the check of the second process, `init` mints badge `0x9ee` for the peer and asserts that it arrives ([init/main.rs:812](user/init/main.rs#L812)).
- **Notifications:** the badge is ORed into the word. So you give each signaller its own *bit*, and the waiter decodes a bitmask of who rang.

The kernel also uses badges internally in one place. A freshly badged copy becomes a revocable parent of every copy made from it. Revoking it therefore cuts off exactly the holders of that badge ([cspace.rs](kernel/cspace.rs), `is_parent_of`).

So "identifying peers" is the right intuition. More precisely, a badge identifies *which capability was used*, and one peer can hold several.

#### 2. Where sap departs from seL4

| | seL4 | sap |
|---|---|---|
| Capabilities per message | 3 named, but only **1** actually delivered, always copied | up to **16**, each **moved or copied**, into a range of slots (the *receive window*) the receiver names |
| Notification syscalls | reuses `Send`/`Recv` | separate `SIGNAL` / `WAIT` / `POLL` |
| Replies | MCS reply objects (one build option) | MCS reply objects, but no scheduling contexts yet |
| Reusing a reply object that still has a caller waiting | silently unlinks the old caller | refused with `ILLEGAL_OPERATION` |
| Capability to the endpoint the message travels on | "unwrapped" into just its badge | no unwrapping |
| IPC error code | in the message info | in `a7`, since `a1` carries the sender's own label |
| Above the kernel | — | Cap'n Proto interfaces, rings as the main data path, the object store, CHERI planned |

The capability-transfer row is the reason sap has its own kernel. Native move is what `$own` will need in M6.

#### 3. Code map

- **[abi/lib.rs](abi/lib.rs)**: the shared contract between kernel and user programs. Syscall numbers, error codes, labels, rights, the `MessageInfo` bit layout, and the 2 KiB `IpcBuffer` and `BootInfo` structs. Both sides depend on it, so they can't drift apart.
- **kernel/**
  - Boot and memory: `boot`, `mm`, `devicetree`, `arch/riscv/{entry, paging, vspace}`.
  - Traps: `arch/riscv/trap.rs`, which saves user registers straight into the current thread's TCB, then [syscall.rs](kernel/syscall.rs) dispatches.
  - Capabilities: `cap`, `cspace`, `untyped`, and `invocation` (operations on kernel objects through `CALL`).
  - Threads: `thread`, `sched`.
  - IPC: [endpoint.rs](kernel/endpoint.rs), [notification.rs](kernel/notification.rs), `fault`.
- **user/libsap**: a thin wrapper for each kernel object (`cnode`, `untyped`, `vspace`, `tcb`, `notification`, `ipc`). On top of those it has three larger pieces:
  - `process.rs`, an ELF loader;
  - `ring.rs`, the shared-memory rings;
  - `sys.rs`, the raw `ecall` and the IPC buffer, found through the `tp` register.
- **user/init**: the root task. Today it is mostly the kernel's test suite, one `check_*` function per feature.
- **user/peer**: the second program. `init` loads it twice: once for the cross-process call and isolation fault, once for the ring echo.

#### 4. IPC from a program's point of view

**Server.** Receive once, then loop on `reply_recv`, which is "answer the last caller, then wait for the next" in a single system call ([init/main.rs:466](user/init/main.rs#L466)):
```rust
let mut m = ipc::recv(ep, reply, &mut words)?;              // lend reply object, block
loop {
    // m.badge = which client; m.info.label() = which operation
    m = ipc::reply_recv(ep, reply, 0, &answer, &[], &mut words)?;
}
```
**Client.** One line ([peer/main.rs:29](user/peer/main.rs#L29)):
```rust
let r = ipc::call(ep, /*label*/ 1, &[1,2,3,4,5,6], &[], &mut out)?;
```
**Sending capabilities.** Pass `&[Give::copy(c), Give::moved(d)]`. The sender's endpoint capability needs the `GRANT` right. The receiver must first call `ipc::set_receive_window(cnode, first_slot, count)`. It then learns how many capabilities arrived from `info.extra_caps()`; they sit in the first slots of the window. A reply can carry capabilities only if the caller's capability had `GRANT_REPLY`.

**Waiting for calls and doorbells together.** Bind a notification to the server thread with `tcb::bind_notification`. Its `recv` then also returns when the notification is signalled, with `source == recv_source::NOTIFICATION` and the signal bits in `badge`.

**Rings** ([ring.rs](user/libsap/ring.rs)). `Producer::send(&words)` and `Consumer::recv(&mut out)` work on shared pages. There are no system calls at all while both sides keep up.

#### 5. One level down

**Tracing the peer's `CALL` into `init`:**

1. **libsap.** `load` writes the words into the IPC buffer. `raw` copies words 0–3 into `a2`–`a5` and sets `a0` = endpoint CPtr, `a1` = `MessageInfo(label, ncaps, len)`, `a6` = 0 and `a7` = `CALL`, then runs `ecall` ([ipc.rs:22](user/libsap/ipc.rs#L22)).
2. **Trap and dispatch.** The trap handler saves the registers into the peer's TCB. [`syscall::handle`](kernel/syscall.rs#L25) sees `CALL` on an endpoint and goes to IPC. (`CALL` on any other object is an operation on that object instead, which is how `sys::invoke` works.)
3. **Lookup and rights.** `ipc()` looks the CPtr up in the peer's CSpace and gets `Cap::Endpoint { ptr, rights, badge: 0x9ee }`. It checks the `WRITE` right ([syscall.rs:94](kernel/syscall.rs#L94)).
4. **Handoff.** [`endpoint::send`](kernel/endpoint.rs#L207) checks whether a receiver is queued. If `init` is waiting, the kernel takes it off the queue along with the reply object it lent. `transfer` then:
   - copies the four register words TCB to TCB;
   - copies words 4 and up from one IPC buffer to the other through the kernel's direct map of RAM;
   - moves or copies the capabilities, if the sender has grant;
   - writes `init`'s results: `a0` = badge, `a1` = info, `a6` = `MESSAGE`, `a7` = OK.

   If nobody is waiting, the sender is queued as blocked-on-send with its badge and rights saved, and `recv` does the same transfer later.
5. **Blocking on the reply.** `after_delivery` links the peer to `init`'s reply object and blocks it in `BlockedOnReply`.
6. **Answering.** `init`'s `reply_recv` finds the caller in the reply object, `transfer`s the answer back with badge 0, makes the peer runnable, and then receives on the endpoint again.

**Why reply objects.** The right to answer a call lives in an object, not in the server thread. One thread can therefore hold several unanswered callers (one reply object each), and scheduling contexts can later follow the reply back to the caller ("time donation").

**Rings** (one channel = two pages per direction):
- **Ownership:** the producer owns the data page (slots plus its index) and the consumer owns a control page (its index). Neither side can corrupt the other's index.
- **Publishing:** a release store of the index publishes a message, and an acquire load on the other side sees it.
- **Not losing a wake-up:** a side that is about to sleep sets its "waiting" flag, runs a SeqCst fence and checks the ring once more. The other side, after publishing, runs a fence and signals only if the flag is set. The two fences guarantee that at least one side sees the other's write, so a wake-up can't fall between "check" and "sleep".

#### 7. Is all the `usize` okay?

For the ABI, yes. Anything that crosses in a register is a machine word, and seL4 uses `seL4_Word` the same way. The costs show up in three other places:

1. **Arguments are easy to swap.** `untyped::retype(untyped, object_type, size_bits, node, offset, count)`, `Process::give(&p, index, cap, rights)` and `map_frame(frame, vspace, va, rights, attrs)` take mostly `usize`s, and swapping two of them compiles fine. `#[repr(transparent)]` newtypes like `CPtr`, `Rights` (the kernel already depends on `bitflags`) and `Badge` cost nothing at runtime and keep the same ABI. libsap already does this for `Error` and `MessageInfo`. I'd do it in libsap's API and leave the plain constants in `abi`, which matches your earlier preference for plain constants.
2. **CHERI.** The kernel stores pointers as integers (`Cap::Endpoint { ptr: usize }`, `blocked_on: usize`), and userspace turns integers into pointers (`RING_BASE as *const Data`, `tp` → `&mut IpcBuffer`). On non-CHERI hardware that's fine. On purecap CHERI, an integer carries no capability tag and can't become a pointer again. Rust's stable strict-provenance APIs (`with_exposed_provenance`, `.addr()`) at least mark the places that would need to change. How the kernel represents object pointers under CHERI is a real question for M10.
3. **Arithmetic on values a peer controls.** In [ring.rs:98](user/libsap/ring.rs#L98), `produced - consumed` reads `consumed` from a page the other process writes. A hostile consumer that moves its index past the producer's makes this subtraction **panic in a debug build**. In release it wraps around, the producer thinks the ring is full and waits, which is no worse than a consumer that stops reading. Use `wrapping_sub` there so the behaviour is deliberate. The kernel side is already careful here (`checked_add` in `transfer_caps`).

Anything sent between machines or stored will be fixed-width through Cap'n Proto, so `usize` never leaves the machine.

#### 8. Is the Cargo layout and the `build.rs` setup good?

**What's there:**
- Five independent packages and no workspace.
- `kernel/build.rs` runs a nested `cargo build` of `init` (release mode, its own target directory, run from `init`'s directory so its `.cargo/config` applies, with `RUSTFLAGS` cleared). `init/build.rs` does the same for `peer`. Each embeds the result with `include_bytes!`.

**What's good:**
- It works on stable Rust.
- The user crates get their position-independent flags without affecting the kernel.
- The separate target directories avoid a deadlock on Cargo's build lock.
- `cargo run` in `kernel/` builds and boots everything.

**Problems:**
1. **A real bug (reproduced).** `init/build.rs` doesn't list `abi/` in `rerun-if-changed`. I touched `abi/lib.rs` and rebuilt: `init` was rebuilt, but the embedded `peer` kept its 10-14 timestamp. Renumber a syscall and `peer` runs the old numbers. The fix is one line.
2. **It doesn't scale.** Every embedded program adds either another nesting level or another build-script stanza. The nested-build code and the linker arguments are already duplicated, and `panic = "abort"` appears in three manifests.
3. **Lockfiles.** Three are tracked, plus two stray untracked ones in `abi/` and `user/libsap/`, probably from cargo or rust-analyzer running in those directories. Those directories have no `.cargo/config`, so a build there targets your host. The stray `user/libsap/target/` also falls inside the kernel's watch on `user/`, which causes spurious reruns. Shared dependencies (`elf` 0.8.0) currently agree across the lockfiles, but nothing keeps them in sync.

**Recommendation:**
- **Now:** fix the `rerun-if-changed` bug and delete the stray lockfiles and target directories.
- **Optional:** a workspace, for one lockfile, shared profiles and simpler rust-analyzer setup. The nested builds can keep their own target directories.
- **The real fix comes with M7's boot image.** The kernel should embed only `init`, and one tool (a `cargo xtask` that builds the user programs, packs the boot image, builds the kernel and runs QEMU) replaces the build-script chain. Oxide's Hubris builds its images this way. Cargo's own answer, artifact dependencies (`-Z bindeps`), was unstable last I knew. I1's sap target then replaces the per-crate `.cargo/config` flags.

#### Capability spaces: trees, lookup, balancing

There are two different trees, and only one of them is involved in lookup.

**The CSpace tree** decides how capabilities are *named*. Lookup cost depends on the number of *levels*, not the number of capabilities, and a single CNode is already a flat array. `resolve` ([cspace.rs:88](kernel/cspace.rs#L88)) does this at each level:
1. Take the CNode's `guard_bits + radix` bits from the top of what's left of the CPtr.
2. The guard bits must equal the CNode's guard.
3. The radix bits index a slot.
4. If bits remain and that slot holds a CNode, repeat from there.

`init`'s CSpace is one level: 4096 slots, with a 52-bit zero guard. CPtr `42` checks that the top 52 bits are zero, uses the low 12 bits as the index, and is done: one compare, one shift, one load. Every process the loader creates is also one level (64 slots with a 58-bit guard). So sap is already flat in practice.

The extra levels are optional, like levels in a page table, and they exist for:
- **Growing** without the kernel allocating anything: you add a second-level CNode instead of reallocating, which would rename every capability.
- **Sharing** a sub-CNode between processes.
- **Handing** a child a sub-space, or moving many capabilities as one.

A fully flat, growable table like Fuchsia's handle table or Unix file descriptors needs a kernel heap. seL4 and sap avoid that on purpose: all kernel memory comes from untyped memory that userspace holds.

**Auto-balancing isn't done, and can't be done transparently.** A CPtr *is* the path, the way a virtual address is. Rebalancing would rename capabilities whose numbers programs have stored in their own memory, which the kernel can't see. Layout is the runtime's choice, and a runtime could re-lay out its own space if it updated its own handles.

**The derivation tree** records where each capability came from. It is stored as a flat linked list through the slots, and only copy, delete and revoke touch it, never lookup.

**The two ways of naming a slot:**
- **Syscalls** take a plain CPtr, resolved from the thread's root at the full 64 bits.
- **CNode operations** take (root, index, depth). `root` is a CPtr to a CNode, and `depth` says how many bits of `index` to resolve from there. That lets you name an empty slot, or a slot that holds a CNode without descending into it.

**The TCB's own slots** ([thread.rs:24](kernel/thread.rs#L24)) are four slots inside the thread object itself. They aren't part of any CSpace, so no CPtr reaches them.

| Slot | Holds | Used for |
|---|---|---|
| `CSPACE_SLOT` | the root CNode | where this thread's CPtrs are resolved |
| `VSPACE_SLOT` | the root page table, with its ASID | the address space the thread runs in |
| `IPC_BUFFER_SLOT` | the frame under the IPC buffer | where long messages are read and written |
| `FAULT_SLOT` | an endpoint | where this thread's faults are sent |

They're filled with *copies* by `TCB_CONFIGURE` and `SET_FAULT_HANDLER`. Because they are real slots in the derivation tree, revoking that endpoint or deleting that address space reaches into the thread too.

`init_slot` in `abi` is something else. It's the conventional numbering of `init`'s ordinary CNode, telling `init` where the kernel put things at boot. The peer's slots 1 and 2 are likewise just a convention `init` and `peer` agree on, standing in for the typed bootstrap message planned for M7.

#### Badges and notifications

**CPtr versus badge.** You have it right the second way. A CPtr is the holder's private name for its own slot and means nothing to anyone else. A badge travels inside the capability and is shown to the *other* side. The receiver never names the sender's capability.

**Who holds what on a notification.** The waiter holds its *own* capability to the same object, usually the unbadged original with the read right. Each signaller holds a differently badged copy with only the write right. In `check_notifications`, `ntfn` is the waiter's capability, and `one` and `two` are write-only copies with badges `0b01` and `0b10`.

**How ORing gives one bit per signaller.** That's a convention: whoever mints the copies gives each signaller a badge with a single distinct bit (`1 << i`). A signal ORs that bit in, and `WAIT` returns the OR of everyone who rang since the last wait. Two rings from the same signaller collapse into one bit: the meaning is "rang at least once", not a count. Endpoint badges aren't ORed; each message carries the whole word, so an endpoint badge can be any number, such as an object id.

**Word size.** Yes, it's 64 bits on RV64 and would be 32 on RV32. That doesn't limit how many capabilities you have. It limits how many signallers *one notification* can tell apart, if each gets a bit. Beyond that you share bits (the bit means "check this group") or use more notifications. sap only targets 64-bit, so I'd fix badges at 64 bits in the kernel interface schema (roadmap D5) rather than leave it platform-dependent.

#### Kernel invocations

A kernel invocation uses the same `CALL` syscall as endpoint IPC. `a0` is a CPtr to the object's own capability (an untyped region, a TCB, a frame). The kernel looks it up:
- if it's an endpoint, the call is IPC;
- otherwise the kernel itself answers, choosing the operation by capability type and label (`abi::label`).

Arguments go in the message words and extra capabilities in the IPC buffer. The answer comes back with its label as an error code. For example, `untyped::retype(ut, …)` is `invoke(ut, UNTYPED_RETYPE, [type, size, index, depth, offset, count], [root])`. There's no separate "kernel capability": the object's capability is the address.

Error conventions differ between the two paths (label versus `a7`), so a userspace stand-in for a kernel object isn't transparent yet. D5 would unify that.

#### libsap, spawn, and `extern "C"`

**Is libsap mostly what would be in std?** Only partly:

| Part of libsap | What it corresponds to | Where it belongs |
|---|---|---|
| `_start`, `sap_start`, panic handler, `print!` | the language runtime | becomes std's platform layer |
| `sys`, `cnode`, `untyped`, `vspace`, `tcb`, `notification`, `ipc` | the system-call interface (libc's role under std; libsel4 in seL4) | stays below std; std would be built on it |
| `process` (loader), `ring` | libraries above std | the process manager, and an IPC transport crate |

A later split could be `sap-sys` (generated from the D5 schema), the runtime, and separate crates for the transport and the loader.

**Should `spawn` live in libsap?** Yes. `spawn_with` in `init` does exactly what `std::thread::spawn` would on sap: retype a TCB, page tables and frames, map a stack and IPC buffer, configure the thread, set its registers. What's missing is resource management: the caller passes untyped memory, slot numbers and a free address range by hand. I'd move it now as `libsap::thread::spawn`, taking explicit resources the way `process::load` takes `Parent` and `Slots`, and add slot, untyped and address-range allocators behind it later.

**Why is the entry `extern "C"`?** A new thread starts with `pc` set to the function's address and its arguments put in `a0`–`a2` by `write_registers`. Only a defined calling convention guarantees the function looks for them there. `extern "C"` means the RISC-V psABI. Rust's own ABI is unspecified and may change between compiler versions. The `-> !` is there because nothing called the function, so there is nowhere to return to (`ra` is meaningless). `sap_start` is `extern "C"` for the same reason: it's called from assembly. `sap_main` can stay Rust-ABI because Rust code calls it.
