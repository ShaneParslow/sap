I don't think the IPC design is doomed. The six system calls per page come from how I built page transfer, not from what moving ownership has to cost. And the copy / volatile split you want to keep is close to the end state, not a stopgap.

**Where we are.** M5 is done, and M7, the process manager, is next on the roadmap. Page transfer works but loses to copying on QEMU at every size up to 60 KiB. Measuring on the D1 waits on your USB-serial stick, and the board also still doesn't show up in FEL mode.

**Why six calls isn't the real cost.** Each page goes through generic seL4-style calls: the sender maps, unmaps and checks the page when it comes back, and the receiver checks, maps and unmaps. We can make the cost per message instead of per page. The kernel would unmap the frames from the sender, check them and map them read-only for the receiver as part of the call itself, as L4 did. That leaves a call, a reply, some page-table edits and one TLB flush. The flush is the true floor on paging. With more than one hart it means interrupting the other harts to flush theirs, which is historically why page-flipping schemes rarely beat copying.

QEMU also exaggerates system calls relative to copying. On the D1, whose core copies memory slowly, transfer may come out ahead sooner, but that needs a measurement.

**Do we drop the no-write guarantee?** Mostly we already have, and that's fine. The guarantee matters only for a message's structure: pointers, lengths, and text handed out as `&str`. Raw bytes don't need it. If a peer changes them mid-read you get garbage, not memory unsafety. Also, "volatile" isn't insecure: it's memory-safe, it just doesn't promise a consistent snapshot. That suggests three tiers:
1. **Structure and small messages:** copy through the ring. The guarantee is free.
2. **Large raw data:** a shared buffer read through a volatile byte type instead of `&[u8]`. Programs copy out what they need or stream it. Wayland, virtio and io_uring all work this way.
3. **Large structured messages from an untrusted peer that must be read in place:** transfer. This should be rare, so its cost matters less.

**CHERI.** You're right that there's no instruction for it. A CHERI capability is a value: giving one away leaves the sender's copies intact, and taking them back means sweeping memory. Two things come close:
- **Linear capabilities** are your "that would be cool" idea, and it has been proposed. Hardware refuses to duplicate them, and moving one clears its source. They appear as an incomplete experimental feature in the CHERI ISA version 7 report, and the StkTokens paper builds on them. No hardware has them and they aren't in the RISC-V CHERI standard. The unsolved parts include a holder that never gives one back, mixing them with ordinary capabilities, and copying memory that contains one.
- **Lending, which works today in CHERIoT.** A capability without the Global permission can only be stored on the stack, and the compartment switcher zeroes the stack after each call. So a callee can't keep a capability lent this way. That normally restricts the receiver, but you can turn it around. A trusted buffer owner lends the sender a writable local capability only for the length of a "fill" call, then gives the receiver a read-only one. The sender has no way to have kept write access, and no page tables are involved. It only works between compartments in one address space.

**CHERI sooner?** I'd do a time-boxed spike now, in parallel, but not move purecap Rust userspace earlier: that still has no 64-bit CHERI-RISC-V compiler. Plain RISC-V code runs unchanged on CHERI-QEMU in hybrid mode. So the spike would be:
1. Get the kernel booting there, saving and restoring the capability registers on context switches.
2. Build one hand-written compartment transport, using assembly or CHERI C for the capability handling, and measure it next to the rings.

That tells us early whether CHERI changes the IPC design, without making M6–M9 depend on it. Paging stays the baseline, as the design principles require. The first decision is which CHERI-RISC-V variant to target, which is already an open question in the wiki.

**The process manager (M7) while LLVM builds.** Most of the tangle you describe isn't needed for M7. The mechanics already exist: `sap_loader::load` builds a process from a position-independent ELF, and `init` puts capabilities into fixed slots and passes three words in registers. M7 turns that into a service with a protocol:

1. **`init` becomes the process manager.** Its checks move into a `check` program that it spawns. That program is the factory's first client, so every boot exercises the whole M7 path.
2. **Boot pack.** `init`'s build script bundles the programs (`peer`, `check`) into an embedded table, with each program named by the hash of its ELF bytes. A real boot image and code objects in the store come later.
3. **Startup record.** Instead of three argument words, `a0` points to a fixed record defined in `abi`: IPC buffer, stack, the free slot range, and the runtime's slots. Those runtime slots are its own CNode, address space and thread, a memory quota, and the connection to its launcher.
4. **Bootstrap message.** The first message on the launcher connection is a Cap'n Proto struct, the program's imports, declared in its own `.capnp` file. The capabilities travel alongside it through the kernel's capability transfer. Launcher and program agree on the type because they were built from the same schema; nothing checks a schema hash yet.
5. **Factory.** `spawn(code hash, bootstrap)` returns a `Process` capability with `wait` and `kill`. The manager is each child's fault handler, so both exits and crashes reach it, and it tells the parent.

The wiki already has a page for each of these, and none of them blocks M7, so they're explicitly deferred:
- schema hashing, and the imports and exports metadata on code objects;
- code objects in the store;
- starting servers on demand;
- the powerbox (granting access at the user's request);
- loaders for other formats such as Wasm;
- thread-local storage and `std`.

- **Capabilities inside the bootstrap struct.** Real Cap'n Proto capability fields need capnp-rust's capability-table support, which normally comes with its RPC layer, and we don't use RPC.
