#### What worked

- **Board run.** You remembered right, and it's better than "minimal": sap's code didn't change at all. The board needed only:
  - a `memory` node and a CLINT node added to the device tree;
  - a small machine-mode stub that turns the caches on;
  - a watchdog armed before each run, so the board resets itself afterwards.

  That supports the "boring hardware" principle, and it gave us the first real numbers. A system call (yield) takes 0.7 µs with caches on, against 10.3 µs with them off. Copying through the ring beats page transfer at every size up to 60 KiB (391 µs vs 1,081 µs at 60 KiB). About half of each transferred page's cost turns out to be the flush of the address-translation cache (TLB) that every map and unmap ends with.
- **CHERI kernel work.** The changes are small and behind the `cheri` feature (13 `cfg` sites). The kernel saves user registers as whole capabilities, bounds user threads to user addresses with `USER_ROOT`, and gives each thread its own DDC (the capability its ordinary loads and stores go through). Pages can hold capabilities only when the mapping asks for them. The kernel's own Rust code never touches capabilities.
- **The toolchain in-tree.** All three forks (compiler, emulator, firmware) build from `toolchain/build.sh`, and nothing needs installing outside the repository.
- **M7 (the process server).** `init` now serves the process factory:
  - `SPAWN` starts a program by its hash, `WAIT` reports how it ended and gives its memory back, and `KILL` ends it.
  - The client supplies the memory the new process is built from.
  - Ending a process is a single revoke of that memory.
  - The loader returns errors instead of crashing.
  - The kernel checks moved out of `init` into a separate `check` program, which `init` starts.

#### What didn't work, or is still open

- **Page transfer as built is a loss** on both real hardware and QEMU. It needs either a cheaper way to map pages per message (range calls, or remapping folded into the call, as L4 did) or CHERI. That's open question 25.
- **Small messages are slower than I'd expect.** A 256-byte round trip on the board takes 17.3 µs, while a yield takes 0.7 µs. On one core, every ring message means a wake-up and a context switch, plus Cap'n Proto encoding and decoding. I haven't profiled where the time goes, but it's worth doing before we draw conclusions about ring IPC.
- **CHERI so far only adds capability support underneath the existing design.** Every process gets the same `USER_ROOT`, so capabilities don't separate anything yet that page tables don't already. Purecap Rust still has no compiler for 64-bit CHERI-RISC-V, and the CHERI timings on QEMU are emulation artefacts, not data.
- **Two M7 items are left:** programs don't start their runtime from the bootstrap message automatically, and the loader isn't on the runtime's slot allocator yet.

  - [prog-loading.md](docs/programs/prog-loading.md) says "Proposed; nothing is built."

#### Do the process-server interfaces suit the long-term vision?

Here's what was actually written: two bootstrap schemas ([check.capnp](interfaces/check.capnp) and [peer.capnp](interfaces/peer.capnp)), and the factory protocol itself as hand-packed constants ([abi/lib.rs:441](abi/lib.rs#L441)). The factory isn't a schema.

**The semantics fit the vision well:**
- no fork or exec;
- code named by its BLAKE3 hash;
- the bootstrap is a Cap'n Proto struct, which is the "world" idea;
- the process handle is a capability;
- the client pays for its child's memory, and revoking that memory destroys the child.

The pay-and-revoke part is the strongest piece. Resources are accounted to whoever asked for them, which is what owner control needs, and teardown is one operation. I'd keep all of these.

**The encoding doesn't fit yet:**
1. **Capabilities in a bootstrap are `UInt32` import indices.** A world is meant to declare the authority a program asks for, by type, so a launcher or the powerbox can show it and refuse it. `endpoint :UInt32` says nothing. This is the biggest gap.
2. **The factory isn't a schema at all.** It has no hash identity, and the bootstrap message is limited to 912 bytes because it's packed into IPC words.

Both are marked as temporary with TODOs pointing at M6, and nothing else depends on them yet. The risk is building more clients on the word protocol before M6 lands.

A smaller point: `LOAD_FAILED` doesn't tell a client how much memory it should have given, so clients will have to guess.

#### How this moves the broader picture

The kernel layers (M1–M5, most of M7) are real and run on a real board. The layers that make sap distinctive are still design:
- capabilities in Cap'n Proto messages (M6);
- typed worlds;
- the object store;
- the powerbox.

Of the three bets this work tested:
- **Portable, boring hardware:** confirmed.
- **Cheap shared-memory IPC:** half confirmed. The ring copy is fine; page transfer isn't.
- **CHERI makes it faster:** the kernel side is ready, but there's nothing to measure until a compartment transport exists.

#### What next (my recommendation, in order)

1. **Housekeeping.** Write up the three sessions, fix the stale pages, put the board scripts in the repository, and decide whether `cheri` merges into `master`.
2. **Use the process factory as design exercise D1** (specify one small interface completely). It's a real interface, and `check_factory` is already its conformance suite. Writing out its schema, ownership, failure modes and idempotency would show what the spec format is missing, on something we actually depend on.
3. **M6** (capabilities in Cap'n Proto messages, with `$own`/`$borrow`). This is the critical path. It turns bootstraps into typed worlds and the factory into a real interface, and everything above the kernel waits on it.
4. **In parallel:** profile the 17 µs small-message round trip on the board, then choose between per-message remapping and the CHERI compartment transport for large messages.
